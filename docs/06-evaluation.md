# Как оценивать качество и пользу

Я разделяю технические тесты, оценку извлечения и поиска, экспертное качество и результат в работе пользователя. Успешный запрос к Mistral подтверждает доступность API; он ничего не говорит о качестве клинического аудита.

| Уровень | Метрика и знаменатель | С чем сравнивать | Статус |
|---|---|---|---|
| Извлечение | Precision/recall фактов и правильность времени, единиц, отрицаний на размеченных фрагментах | Регулярные правила и структурированная выгрузка | План |
| Поиск | Recall@5: доля размеченных релевантных фрагментов, найденных в первых пяти результатах; среднее по запросам | BM25 против гибридного поиска | План |
| Обоснование | Доля выводов с существующей ссылкой; отдельно доля ссылок, действительно подтверждающих вывод | Ручная проверка двух экспертов | План; цель для существования ссылок 100% |
| Дефекты | TP/(TP+FP) и TP/(TP+FN), отдельно по значимости и классу | Ручной чек-лист, формальные правила, правила + RAG + модель | План; ориентиры проекта: recall критичных ≥95%, precision ≥90% |
| Полезность | Принятые экспертом рекомендации / рассмотренные рекомендации | Слепая оценка результата без названия модели | План; ориентир проекта ≥90% |
| Время | Медиана и разброс минут на карту, включая проверку ответа и исправления | Один и тот же набор в обычном процессе и с помощником | Базовое время организации неизвестно |
| Нагрузка | Лишние замечания на карту, доля карт без полезного результата, число ручных уточнений | Ручная проверка | План |
| Надёжность | Завершённые запуски / все запуски, задержка, токены, ошибки схемы | Одинаковые случаи и настройки | Сейчас есть только технические проверки |

Пороги служат проектными ориентирами, а не результатами эксперимента. При небольшом наборе обязательно покажу абсолютные TP, FP, FN и интервалы неопределённости. Нулевое число ошибок на десятке примеров не докажет 95% полноты. «Доля правильных ответов» без числа положительных и отрицательных примеров может скрыть пропуски редких критичных дефектов.

## Сравнительный эксперимент

Сначала эксперт размечает случаи без ответов системы. Затем сравниваю ручной чек-лист, формальные правила, RAG без генерации и RAG с Mistral. Модель, параметры, корпус и версия каждого входа фиксируются. Состав набора одинаковый; варианты одной базовой истории не пересекают части. Промпт и параметры настраиваются только на открытой части.

В пользовательском испытании меняю порядок условий между участниками и учитываю повторное знакомство с картой. Измеряю всё время проверки, а не только скорость ответа сервера. Для разметки использую два независимых заключения и разбор расхождений. Межэкспертное согласие сообщаю отдельно от качества модели. Доступа к врачам для такого испытания пока нет.

## Что показывают опубликованные результаты

В РКИ Lukac et al. участвовали 238 амбулаторных врачей 14 специальностей в США. Относительно контроля Nabla уменьшила время написания записи на 9,5%: 95% ДИ изменения от −17,2% до −1,8%. Для DAX изменение составило −1,7%, ДИ от −9,4% до +5,9%; статистически значимого эффекта по этому исходу не показано. Период испытания: 04.11.2024–03.01.2025. Это пример измеренного эффекта на конкретной задаче, а не ожидаемая экономия моего проекта. [RCT](https://doi.org/10.1056/AIoa2501000)

Для российских продуктов в изученных публичных описаниях нет общего испытания на одном открытом наборе с одинаковыми метками. Поэтому я сравниваю их функции и качество доказательств, а рейтинг по точности не строю. Собственный набор сначала должен пройти экспертное согласование.
