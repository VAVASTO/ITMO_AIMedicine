# Как оценивать качество и пользу

Я разделяю технические тесты, оценку извлечения и поиска, экспертное качество и результат в работе пользователя. Успешный запрос к Mistral подтверждает доступность API; он ничего не говорит о качестве клинического аудита.

| Уровень | Метрика и знаменатель | С чем сравнивать | Статус |
|---|---|---|---|
| Извлечение | Precision/recall фактов и правильность времени, единиц, отрицаний на размеченных фрагментах | Регулярные правила и структурированная выгрузка | План |
| Поиск | Recall@5: доля размеченных релевантных фрагментов, найденных в первых пяти результатах; среднее по запросам | BM25 против гибридного поиска | План |
| Обоснование | Доля выводов с существующей ссылкой; отдельно доля ссылок, действительно подтверждающих вывод | Ручная проверка двух экспертов | План; цель для существования ссылок 100% |
| Дефекты | TP/(TP+FP) и TP/(TP+FN), отдельно по значимости и классу | Ручной чек-лист, формальные правила, правила + RAG + модель | План; клинические пороги ещё не согласованы |
| Полезность | Принятые экспертом рекомендации / рассмотренные рекомендации | Слепая оценка результата без названия модели | План; допустимый уровень согласует эксперт |
| Время | Медиана и разброс минут на карту, включая проверку ответа и исправления | Один и тот же набор в обычном процессе и с помощником | Базовое время организации неизвестно |
| Нагрузка | Лишние замечания на карту, доля карт без полезного результата, число ручных уточнений | Ручная проверка | План |
| Надёжность | Завершённые запуски / все запуски, задержка, токены, ошибки схемы | Одинаковые случаи и настройки | Есть технические проверки, первая проба GLM и 36 новых ответов в трёх условиях на 12 историях; без повторов |

Ранее указанные recall ≥95%, precision ≥90% и доля принятых рекомендаций ≥90% были предварительными ориентирами без расчёта размера выборки и согласования с экспертом. Для приёмки их пока не использую. Сначала нужно определить значимость дефектов, допустимое число пропусков и ложных замечаний, затем рассчитать объём независимой проверки. При небольшом наборе покажу абсолютные TP, FP, FN и интервалы неопределённости. Нулевое число ошибок на десятке примеров не докажет 95% полноты.

## Инженерная приёмка ближайшей версии

Ниже зафиксирован план приёмки полной функции. После проверки структуры данных провёл отдельную пробу GLM: 14 целевых статусов совпали с ожиданиями, но в одном объяснении нашёл сведения из будущего документа. Это не закрывает приёмку функции; результаты пробы приведены в разделе проверок. Ожидания относятся к конкретному критерию и не оценивают качество медицинской помощи целиком.

| Проверка | Условие прохождения после реализации | Чем подтверждать |
|---|---|---|
| Заданные ситуации | 14 из 14 вариантов дают ожидаемый статус по целевому критерию | Журнал по каждому `case_id` и сравнение с отдельным файлом ожиданий |
| Время | В варианте 03 поздний документ исключён; в 14 документ ровно на границе включён. В использованных основаниях 0 документов из будущего | Список доступных документов и ссылки в результате; отдельные тесты неизвестной даты |
| Пропуски и исключения | В 02–05 отсутствие подтверждения не превращается в утверждение о невыполнении; в 06–07 нужен эксперт | Статусы и объяснения, без автоматически подтверждённого исключения |
| Границы | В 08–10 набор по ВП не применяется; в 13 неизвестный возраст остаётся неизвестным | Причина отказа от проверки; отсутствие клинических замечаний по неподходящему правилу |
| Коды | В 11 сохранены оба кода; диагноз автоматически не изменён | Ссылки на выписку и поле счёта; сопоставление входа и результата |
| Источники | В 12 нормативный вывод не создаётся; во всех вариантах неизвестная актуальность версии явно сохраняется | Версия и статус источника в результате, без подмены исследовательской копии действующим основанием |
| Контракт C07 | Каждая ссылка существует, цитата совпадает с доступным текстом; вывод содержит все обязательные поля | Контрольные ответы с несуществующим ID, изменённой цитатой, ссылкой на будущий документ и пропущенным полем должны отклоняться. Корректный контрольный ответ должен проходить |
| Ошибки API и разметка | Каждый запуск отражён в журнале, включая ошибку; ожидаемые статусы не передаются модели | Сохранённые входы без ключей, результат или причина ошибки; локальный ответ не выдаётся за ответ API |

Требование 14/14 служит проверкой реализации заданной спецификации. Его выполнение не оценивает обобщение на новые карты: варианты принадлежат одной исходной семье. Для закрытого испытания нужны новые семьи, размеченные до запуска модели. Порог по времени ответа назначу после первых измерений; пока сохраняю задержку и расход токенов без произвольного обещания скорости.

## Сравнительный эксперимент

**Гипотеза:** явный учёт времени доступности фактов и применимости требований уменьшит число необоснованных замечаний по сравнению с одним запросом по всей карте. Для проверки полной архитектуры планирую условия ниже. Первый парный эксперимент уже выполнен на 12 новых авторских историях: GLM со всей картой и после отбора документов дала 12/12 совпавших статусов в обоих условиях. Улучшение качества от фильтра не показано. Mistral на тех же отфильтрованных входах дала 10/12. Это обосновывает предварительный выбор GLM для следующей инженерной проверки, но не подтверждает клиническую гипотезу. В сравнении модулей архитектуры модель должна оставаться одной и той же.

| Вариант | Что получает и делает | Что выясняю |
|---|---|---|
| Ручной чек-лист | Специалист проверяет карту и применимые требования без подсказок системы | Качество и время обычного процесса; нужен эксперт |
| Формальные правила | Проверяются коды, даты, наличие связей и доступность документов | Что можно решить без модели |
| GLM одним запросом | Весь текст карты с временными метками и одинаковый небольшой пакет требований, без поиска и предварительного отбора фактов | Исходный вариант для проверки гипотезы; модель сама учитывает время и условия |
| RAG без генерации | Поиск выдаёт источники; замечания формируют только правила | Вклад поиска отдельно от свободного текста модели |
| Полный вариант | Правила + поиск + GLM, фильтрация по времени, проверка применимости, ссылки на оба основания | Результат предложенной архитектуры |
| Без фильтра по времени | Полный вариант, но документы из будущего не исключаются; временные метки остаются | Вклад явного отбора доступных фактов |
| Без проверки применимости | Полный вариант, но отдельная проверка возраста, условий и исключений отключена | Вклад проверки применимости требований |

Это план полного сравнения: выполненная проверка времени охватывает только часть условий и не использует RAG. Последние два варианта предназначены только для эксперимента. Их сравниваю с полным вариантом попарно на тех же историях. Сравнение с одним запросом показывает общий эффект архитектуры; само по себе оно не позволяет приписать улучшение конкретному модулю. От всех вариантов с моделью требую одинаковую схему и два основания замечания: в карте и источнике требования. Для коротких карт пакет источников должен помещаться в контекст всех сравниваемых вариантов. Если объём или доступные источники различаются, фиксирую это как отдельное условие.

Основной показатель для гипотезы: число необоснованных замечаний на карту. Дополнительно считаю пропущенные замечания, использование фактов из будущего, ошибки применимости, неподтверждённые ссылки и корректные ответы «недостаточно сведений». Сокращение числа замечаний не считается улучшением, если система просто перестала находить нужные. Для каждого показателя сохраняю абсолютные числа, знаменатель и разницу между условиями. Два специалиста должны разметить клинический набор до просмотра ответов системы.

Для первой инженерной проверки использую отдельно записанные ожидания по времени и кодам. Дополнительно подготовлены 14 вариантов первой функции: в них есть отказ, отметка об ограничении, неприменимость, отсутствие замечания по целевому признаку и неполные сведения. Это авторские ожидания для разработки, а не экспертная разметка. 12 исходных заготовок, 24 прежних и 14 новых вариантов нельзя смешивать в оценку клинической точности. Успех на них не подтверждает клиническую гипотезу. Закрытую оценку провожу на новых семьях историй после согласования разметки.

Модель, параметры, корпус и версия каждого входа фиксируются. Варианты одной базовой истории не пересекают части. Промпт и параметры настраиваются только на открытой части. Начинаю с одного прогона каждого условия, затем повторяю выбранные условия для оценки разброса, если позволяет бесплатная квота. Число прогонов и ошибки API показываю явно; сохранённый ответ не засчитываю как свежий запуск.

Журнал полного эксперимента должен содержать `run_id`, `case_id`, семью истории, вариант проверки, модель, версии промпта и корпуса, ожидаемый и фактический статусы, ссылки на доказательства, ошибку или отказ, время, токены и число попыток. Из одного журнала строятся таблица сравнения и графики. Если вызов не состоялся, строка остаётся с причиной; результата качества у неё нет.

В будущем пользовательском испытании планирую менять порядок условий между участниками и учитывать повторное знакомство с картой. Буду измерять всё время проверки, включая чтение ответа и исправления. Для разметки потребуются два независимых заключения и разбор расхождений. Межэкспертное согласие укажу отдельно от качества модели. Доступа к врачам для такого испытания пока нет.

## Что показывают опубликованные результаты

В РКИ Lukac et al. участвовали 238 амбулаторных врачей 14 специальностей в США. Относительно контроля Nabla уменьшила время написания записи на 9,5%: 95% ДИ изменения от −17,2% до −1,8%. Для DAX изменение составило −1,7%, ДИ от −9,4% до +5,9%; статистически значимого эффекта по этому исходу не показано. Период испытания: 04.11.2024–03.01.2025. Это пример измеренного эффекта на конкретной задаче, а не ожидаемая экономия моего проекта. [RCT](https://doi.org/10.1056/AIoa2501000)

Для российских продуктов в изученных публичных описаниях нет общего испытания на одном открытом наборе с одинаковыми метками. Поэтому я сравниваю их функции и качество доказательств, а рейтинг по точности не строю. Собственный набор сначала должен пройти экспертное согласование.
