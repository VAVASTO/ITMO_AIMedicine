# Первая функция: проверка полноты истории болезни

Статус: спецификация для следующего этапа. В текущем коде клинический аудит ещё не реализован.

## Сценарий

Врач открывает синтетическую историю болезни взрослого пациента стационара с нетяжёлой внебольничной пневмонией, выбирает момент проверки и запускает анализ. Система возвращает сведения, которые стоит уточнить, противоречия и основания. Врач принимает или отклоняет каждое замечание и при необходимости исправляет запись сам.

Я начинаю с полноты, поскольку результат проще проверить по исходным фактам и источникам, чем план лечения. Функция затрагивает обе части общего проекта: помогает врачу и оставляет проверяемую историю замечаний.

## Вход

Обязательны идентификатор записи, отметка о синтетическом происхождении, возраст, известный диагноз, тип обращения и момент `review_at`. Поля содержат статус, значение, единицу и время доступности. Неизвестная аллергия и явно отрицаемая аллергия различаются. Назначение обследования не считается его результатом.

Промпт не получает ожидаемые коды из `data/expectations.json`. Текст истории рассматривается как данные: вложенные просьбы изменить правила, игнорировать источники или придумать факт не выполняются.

## Выход

| Поле | Смысл |
|---|---|
| `run_id`, `record_version`, `review_at` | Какой снимок записи проверен |
| `status` | `completed`, `insufficient_evidence`, `out_of_scope` или `failed` |
| `findings[]` | Замечания с кодом, объяснением, связанными фактами и основаниями |
| `evidence[]` | `document_id`, версия, `chunk_id`, физическая страница и точная цитата |
| `uncertainties[]` | Что нельзя установить по записи или источникам |
| `review_required` | Нужна ли проверка человеком; для клинических замечаний всегда `true` |

Формулировка должна описывать документ: «В переданной записи не найден результат исследования». Без дополнительных сведений нельзя писать «Врач не назначил исследование». Поле уверенности модели, если появится, не будет трактоваться как калиброванная вероятность.

## Порядок обработки

1. Проверить JSON и область применения. При неизвестной тяжести запросить уточнение, при тяжёлом течении или возрасте до 18 лет вернуть `out_of_scope`.
2. Отобрать факты, доступные не позднее `review_at`; собрать неизвестные и противоречия.
3. Найти основания по заданной версии корпуса. При отсутствии подходящих фрагментов вернуть `insufficient_evidence`.
4. Попросить модель подготовить замечания строго по фактам и переданным основаниям.
5. Проверить структуру JSON, ссылки и цитаты. Не принимать обрезанный ответ и ссылки на отсутствующие фрагменты.
6. Отделить подтверждённые формальные проверки от клинических гипотез, требующих эксперта.
7. Показать результат врачу и сохранить его решение с комментарием.

## Приёмка

| Проверка | Ожидаемое поведение |
|---|---|
| Отсутствующее поле | Замечание не превращается в утверждение о невыполненной помощи |
| Отрицание и неизвестность | «Аллергии отрицает» не равно «сведений нет» |
| Время | Будущий результат не используется |
| Противоречие | Оба значения сохранены, требуется уточнение |
| Несуществующая ссылка | Замечание отклоняется как неподтверждённое |
| Пустой поиск | Нет клинического вывода без оснований |
| Недоступный API | Явная ошибка; демонстрационный ответ не подставляется |
| Случай вне границ | Понятное сообщение без клинического заключения |

Технические критерии можно проверять автоматически. Перечень клинически обязательных полей, правильность замечаний и полезность формулировок должен подтвердить врач. Текущие инженерные метки не заменяют эту проверку.
