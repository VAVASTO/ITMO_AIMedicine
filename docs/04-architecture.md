# Архитектура и поиск по документам

На первом этапе реализованы FastAPI, Vue, настройки, Mistral-клиент и техническая проверка соединения. Описанные ниже клинический процесс, SQLite и RAG предстоит реализовать.

## Процесс проверки

```text
Запись и момент проверки
        ↓
Проверка формата, границ и времени фактов
        ↓
Поиск подходящих фрагментов в версии корпуса
        ↓
Mistral: проект замечаний в JSON
        ↓
Проверка ссылок, цитат и связи с фактами
        ↓
Замечания и неопределённости → решение врача
```

| Модуль | Вход | Выход и ответственность |
|---|---|---|
| Vue | Запись, результат проверки | Форма, список замечаний, просмотр оснований и действие врача |
| FastAPI | Запрос из интерфейса | Проверка формата, идентификатор запуска, вызов нужных модулей |
| Подготовка фактов | Запись и `review_at` | Нормализованные факты, доступные на момент проверки; отдельные неизвестные и противоречия |
| Поиск | Клинический контекст и версия корпуса | Ограниченный набор фрагментов с метаданными и оценкой поиска |
| Адаптер LLM | Инструкция, факты, найденные фрагменты, схема | Структурированный проект замечаний и технические метрики |
| Проверка оснований | Ответ LLM и исходные фрагменты | Принятые замечания либо непроверенные гипотезы; запрет выдуманных ссылок |
| SQLite | Случаи, версии документов, запуски и решения | История изменений и возможность воспроизвести проверку |

## Зачем RAG

Модель не должна вспоминать текст рекомендации по памяти. Поиск подаёт ей выбранные фрагменты известной версии. Это позволяет проверить цитату, обновить документ независимо от модели и установить, какие основания были доступны при конкретном запуске. Само наличие RAG не доказывает, что вывод верен: подходящий источник и смысловая связь с замечанием проверяются отдельно.

## Подготовка корпуса

1. Зафиксировать версию, URL, дату получения, SHA-256 и условия использования документа.
2. Извлечь текст постранично. Сверить таблицы, схемы и страницы с плохим извлечением визуально; помечать страницы, где нужен OCR.
3. Разделить текст по разделам на фрагменты примерно по 300–500 слов. Сохранять номер физической страницы, заголовок, смещения в тексте и соседние фрагменты. Табличную строку не отрывать от заголовков и примечаний.
4. Начать с BM25 как прозрачного базового поиска. На отдельной разметке сравнить его с гибридным поиском по ключевым словам и эмбеддингам.
5. Для каждого найденного основания передавать стабильный `chunk_id`. После ответа проверять существование идентификатора и точное соответствие цитаты нормализованному тексту фрагмента.

Нормализация для проверки цитаты ограничивается пробелами и переносами. Исправления извлечённого текста должны иметь отдельную версию, иначе точное сравнение перестанет быть воспроизводимым. Для формул и таблиц потребуется проверка по изображению страницы.

## Предлагаемое хранение

В SQLite планируются таблицы `cases`, `observations`, `documents`, `chunks`, `audit_runs`, `findings`, `reviews`. Запуск содержит версии входной записи, корпуса, промпта, схемы ответа и модели. Исправления создают новую версию; старый ответ сохраняется. Сам PDF хранится отдельно, в базе остаются путь и контрольная сумма.

Ключ API доступен только серверу. В первый публичный набор входят только синтетические данные. Клинические сведения не пишутся в технический журнал ошибок; там достаточно кода ошибки и идентификатора запуска. Перед работой с реальными данными понадобятся отдельные условия доступа, хранения и обработки.

## Замена модели

Вызывающий код зависит от `StructuredProvider`, а не от конкретного API. Сейчас реализован Mistral. Для Gemini нужно добавить адаптер, сопоставить JSON Schema и метрики ответа, прогнать те же тесты и затем сменить `LLM_PROVIDER`. Одного изменения имени провайдера сейчас недостаточно: неготовый адаптер возвращает явную ошибку.
